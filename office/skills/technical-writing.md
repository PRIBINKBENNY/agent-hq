# Technical writing: docs, READMEs, papers, reports (updated 2026-10-21)
- Lead with the result or the action; put background after. A reader decides in one screen whether to continue.
- One idea per sentence, verbs not nouns, no hedges you cannot back; prefer "the test fails on empty input" to
  "there may be some issues with certain inputs".
- README order: what it is in one line, a picture, install in one command, three usage lines, how to test, licence,
  how to get help. If install takes more than one command, that is the next task.
- Tutorials teach one path start to finish; how-tos solve one problem; reference lists everything; explanation says
  why. Do not mix them in one page (the Diataxis split).
- Numbers carry their unit, their spread and their date; tables for comparisons, prose for narrative; never a
  chart with two y-axes.
- Papers: abstract = problem, method, result with number, why it matters; every claim traceable to a table or a
  citation; limitations are a section, not a sentence; the code link works.
- Reports to Pribin: outcome first, what changed, what needs him, in that order; under 200 words unless he asked
  for detail. No "as an AI".
- Edit pass: cut 20%, replace every "very", read it aloud, check that a stranger could act on it.
Sources: Google Technical Writing courses; Diataxis framework; Strunk and White; the research-publishing guide.
